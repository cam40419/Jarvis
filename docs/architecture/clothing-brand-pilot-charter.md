# Simon platform pilot charter and core acceptance plan

PLAN-01. Updated October 10, 2026. Status: mandatory platform requirements and evaluation contracts grounded in the stdout pilot; architecture choices, workflow-specific thresholds and experiment budgets remain open. This is a planning artifact, not an implementation or deployment record.

Build **Simon as an autonomous project and company workflow platform**, using stdout's existing clothing-brand context as representative input. The platform must ingest a large, rough project, identify missing or conflicting information, assemble and grow a team, manage all work on boards, produce independently checked outputs, and keep the user informed and in control. Stdout tests these reusable capabilities; it is not a parallel brand consulting project or a requirement to finalize the brand before building Simon.

**Complete and test the initial platform core before implementing business tools one at a time**, as requested by the owner. Brand refinement and creative production become in-platform pilot work as the relevant tools pass acceptance. PLAN-01 defines the platform requirements, evaluation contracts and implementation backlog needed to reach that point.

The October 10 owner correction makes change impact and repair, complete usable delivery packets, lower-effort review, reliable recovery with visible costs, and continuity across authorized people and tools **base platform implementation requirements**. They are not optional innovation bets. The base goal is to perform as well as or better than comparable tools serving the same supported goal, under a fair declared scope. CORE-19 through CORE-24 make that goal testable without promising universal superiority over every product or claiming that public feature documentation proves performance.

Read with the [platform plan](autonomous-work-platform-plan.md), [baseline quality implementation plan](platform-baseline-quality-plan.md), [hosting and capacity comparison](hosting-and-capacity-plan.md), [integration work packages](integration-delivery-plan.md) and [delivery roadmap](../next-phases.md).

## First platform milestone

The first milestone is **a reviewable Simon implementation plan and evaluation contract**, grounded in the supplied pilot and reusable across large projects. It should let the owner assess the proposed project-creation experience, automatic team decisions, manual controls, board authority, quality and review process, model settings, cost visibility and recovery behavior before substantial implementation begins.

An end-to-end scenario starts with representative rough files, builds a project charter with explicit unknowns, proposes a team and task graph, executes bounded reference work, independently reviews its artifacts, takes user feedback, and recovers from an interruption. The UI must expose decisions, task ownership, tool activity, artifact versions, costs, blockers and uncertainty throughout. The user can edit the plan or team, reassign work, change allowed models or budgets, and stop execution.

After the core gate and individual tool acceptance, stdout becomes a real in-platform evaluation: Simon can help refine identity, develop Essentials and the first drop, manage creative revisions and operate accepted code/design workflows. Their final brand decisions are outputs of future project work. They are not prerequisites for completing PLAN-01.

Keep platform backlog items and domain pilot tasks separate and traceable. A platform item is complete when its required behavior passes evaluation; producing a brand document manually cannot satisfy that criterion.

PLAN-01 must map the five mandatory base requirements to implementation work and CORE-19–23, and define CORE-24's comparative protocol. Planning completion does not mean those capabilities are implemented. Poor comparative results require improving or redesigning the base and recording current unsupported operations; they do not permit reducing mandatory platform requirements or changing the registered scope to pass a failed comparison.

## Platform creative collaboration contract

Use `brief -> concepts -> owner discussion -> revised direction -> production draft -> agent checks -> owner revision or acceptance -> publication proposal`. Project settings select which checkpoints require the owner; a task can revisit concepts when feedback changes the direction.

Keep the original request, annotated comments, accepted decisions, rejected alternatives and the exact referenced versions. A revision request should carry the conversation and visual references forward. Ask a focused question when feedback conflicts with an earlier accepted constraint; otherwise apply the correction and continue independent work.

Support distinct deliverable types: garment artwork, garment construction/technical material, advertisement, social post, still image and video. Each needs its own dimensions, editable source, target channel/application, quality rubric and proof. Batch a coherent campaign for review while keeping every asset individually inspectable.

An approved creative concept does not automatically authorize ad spend, an order, a public post or a change to the storefront. Those are separate effects governed by the project's configured rules. Changing the asset or material destination after approval requires the applicable new review.

## Definition of the initial core system

The core is a usable, locally deployable SaaS foundation with explicit contracts for future tools. It includes:

- Accounts, isolated tenants/workspaces, membership, configurable platform admin, tenant owner roles and authenticated access to files and history.
- Projects, charter/intake, milestones, native board contracts, human/agent/pool assignment, dependencies, comments, task claiming and concurrent edits.
- Persistent agent roles, AI team composition, bounded delegation, manual overrides, schedules/waits and cancellation.
- A unified model registry and essential model transport, free/local profile, project paid-key setup, capability checks, routing, reservations and enforceable spend policies.
- Generic uploads and file artifacts, immutable versions, previews supported by the core, maker/reviewer tasks, owner comments and acceptance bound to exact versions.
- Typed deliverable dependencies, current applicability and permission checks, propagated stale review, bounded repair and preservation of unaffected accepted work.
- A generic supported delivery-bundle manifest binding editable sources, previews, evidence, check results and limits to immutable component identities; a versioned validator interface and core fixtures proving open/edit/render and unsupported-format behavior.
- A review experience that exposes consequential changes, actual check coverage and the next authorized decision with no greater setup or review burden than the eligible comparative baseline at equivalent quality.
- Durable execution, event correlation, tool-operation ledger, leases, recovery, unknown-outcome handling and local/remote worker enrollment contracts.
- Reliable recovery of accepted work and pending obligations, duplicate-effect prevention/reconciliation, economic liveness and visible incurred costs or unresolved liabilities across failures.
- Authorized human/tool/provider takeover using inspectable current state, editable work and outstanding obligations, with fresh destination authority and no secret or revoked-derived-content export.
- Shared queues, per-tenant entitlements, storage limits, metering and admin overrides. Payment-provider integration is a later individual integration.
- A connector SDK/reference implementation, deterministic fake provider and test fixtures that exercise reads, delayed jobs, writes, failures and reconciliation.
- Working user interfaces for project creation, team/board operation, reviews, connections/models, spending, health, and recovery; repeatable local installation and backup/restore.

One minimal real model transport is essential infrastructure, as are generic local file operations and test/reference tools. Specialized research, Office authoring, image/video generation, interactive web automation, Git/code operations, email/calendar, Shopify and social publishing are later tool packages. Local Git and isolated generator/storefront execution are concrete early post-core requirements; they need not wait for remote GitHub integration. Existing implementations are reuse candidates and must pass their own acceptance before being exposed as supported production tools.

The delivery-bundle and validator contracts are core work. Prove them with core-supported editable files, known previews and reference validators under a recorded environment, including a deliberately unsupported component. A logical deliverable may bind several immutable components through its manifest; each component's identity, disclosure permission, edit/render support and storage accounting must be explicit. This does not require a universal Office or creative authoring engine before the core gate. Each real application adapter, authoring operation and application-specific validator is implemented and accepted individually afterward.

Current artifacts already provide immutable revisions, exact-version decisions and linked repairs. They remain one logical file per task with 1 MiB files, bounded UTF-8 model review, basic text/image previews and no general document renderer, selective cross-deliverable dependency graph or complete bundle validator. Existing model accounting and execution supply useful recovery contracts; they do not establish complete tool/compute/storage economics or comparative parity. CORE-19–24 are requirements to implement and verify, not results attributed to the current slice. See [current artifacts](../runbooks/native-artifacts.md), [execution](../runbooks/native-execution.md) and [model accounting](../runbooks/project-models.md).

“Core complete” proves orchestration and product contracts. It does not certify the quality or reliability of an unimplemented image generator, spreadsheet writer or commerce adapter. Final public SaaS readiness also requires hosted load/security/operations acceptance and the commercial account lifecycle.

### Additional base acceptance contracts

**CORE-19 — change impact and repair.** A sanitized fixture contains at least two accepted deliverables sharing a typed source field and one unrelated deliverable. Record input/source/requirement revisions, field or passage dependencies, validator versions and current authority. Change a material value, paraphrase an irrelevant passage, and revoke one reader or grant in separate resets. Every seeded material must-fail consequence invalidates current review/acceptance along its dependent path, creates an inspectable bounded repair, and requires fresh applicable review. Preserve unrelated bytes and decisions. Never turn a model's uncertain impact judgment into permission to suppress mandatory invalidation. Show unknown dependency coverage; historical acceptance may remain as history while current applicability, disclosure permission and release status are reassessed.

**CORE-20 — complete usable delivery packet.** A core fixture bundles a supported editable source, its preview, bounded supporting evidence, versioned checks, owner decisions, outstanding limitations and intended use. The manifest binds exact component revisions/hashes and the source/check/render environment, with access checked for originals and derived components. Open the source, perform a designated edit, save, reopen and rerender under the declared profile. Detect a mismatched preview, stale check, omitted required component and unsupported format in independent variants. An unsupported application check stays explicit and routes to the required human/specialist decision; it cannot be marked passed. Changing a component invalidates the applicable packet decision. Generic fixtures prove this contract without claiming an unimplemented application can author or validate its native files.

**CORE-21 — lower-effort review.** Present the exact target, meaningful changes, required facts, actual checks, truncation/omission warnings, unresolved findings, cost/uncertainty and the next authorized decision. Time active briefing/setup, review, correction and escalation; preserve all human assistance. Blind defect review must show that making the decision flow easier does not hide defects or reduce quality. The mandatory floor is no greater review/setup burden than the strongest eligible configured baseline for the same quality and supported workflow; further reductions may be targets fixed for that workflow. No universal 30% improvement is required. Bound repairs and make no-progress escalation understandable to the owner.

**CORE-22 — recovery, integrity and economic liveness.** Use fixed failure points around dispatch, checkpoint application, reference write acknowledgement, cancellation and restoration. Preserve accepted bundles, their authority records and pending obligations. Record every incurred generation/review/retry/tool/resource attempt and unresolved liability; customer keys and zero-fee inference do not make other resources invisible. A lost response remains unknown until trusted observation/reconciliation establishes the outcome. Do not retry a potentially completed effect blindly, invent an undo, or release unknown liabilities merely to unblock a queue. Under preregistered time/capacity bounds, unrelated permitted work proceeds where safe and reconciled work can resume; otherwise show the necessary recovery action and accountable owner. Arbitrary external systems are not promised universal exactly-once effects or rollback.

**CORE-23 — authorized continuity.** A takeover packet exposes the permitted brief, current editable components, accepted historical decisions, current applicability, dependencies, failures, liabilities and next safe action. A second eligible person/runtime continues a supported fixture without the maker reconstructing it. Bind every resumed read/write to fresh membership, role, grant, destination and budget checks. Handoff never transfers the exporter's credentials or permission. Revoke a source/reader and ensure originals, extracts, previews, derived claims, memory, logs and exports do not disclose content through the packet. Retained historical decisions do not establish current disclosure rights; any authorized separately shareable publication must have its own explicit decision. Preserve unresolved work and quarantine conflicts instead of silently merging external changes.

**CORE-24 — comparative base gate.** Declare supported job/outcome, formats, fixture versions, model capability/configuration constraints, permitted privacy/data destinations, accounts/tool editions, compute/resource ceilings and total cost treatment. Use reasonably configured eligible same-goal rivals plus a competent person operating their usual board/files, strong assistant and relevant review tools. Enable rivals' applicable capabilities; include setup, human help, repairs, recovery and all incurred/unknown costs. Public-source feature presence selects candidates, not performance winners. An ineligible or untested product is not a failed competitor.

Screen candidates to identify the strongest eligible workflow baseline, then freeze that baseline and preregister quality, completion/liveness, review/setup burden, recovery, native usability, cost and confidence targets before held-out confirmation. Targets require at least baseline performance: higher-is-better measures cannot decline; lower-is-better burden/recovery measures cannot increase at the equivalent quality and allowed resource profile. Report dimensions and uncertainty separately; do not average authority, disclosure, spending, duplicate-effect or data-loss failures into a favorable score. Inconclusive quality/noninferiority evidence does not pass. The core gate covers declared generic/text/file/reference workflows; each later real-tool acceptance extends the comparative gate to its supported operation. This is a tested base standard within scope, not an arbitrary promise to win every market or beat every future product.

## Tool implementation after the core gate

Select and finish one work package at a time. Each package has an output contract, connector operations, resource grants, billing behavior, tests, a real pilot task, owner review, recovery evidence and a documented support boundary. Enable it only after that gate; then choose the next package based on the pilot's current needs.

Candidate tool packages, selected for platform learning and demonstrated pilot need, to enable one at a time:

1. Source discovery/research or richer artifact import, selected against the first intake gap after generic core uploads work.
2. Local Git/code execution for the generator and website: reviewed changes, reproducible builds, tests, artifact handoff and recovery.
3. Image generation/editing or a selected design application, including the full owner revision loop and project-configured source-art policy.
4. A procedural graphics generator with versioned inputs, editable output and independent visual/technical checks.
5. Document production and spreadsheet authoring as separate tools with rendered inspection and calculation checks.
6. Optional shared storage or visual-board synchronization when collaboration requires it.
7. Video/media, website deployment and commerce operations as separate packages when their workflows are selected.
8. Garment CAD, email/calendar, social publishing and other operations according to demonstrated need.

This is a proposed dependency order, not a requirement to build every item or a storefront-provider decision. Each listed alternative or grouped capability still needs an individual implementation gate. Git/code delivery is distinct from ordinary Git use by Simon's developers. Build the generator and website through accepted tools; do not count briefs as implemented systems or require simultaneous connector rollouts. A procedural graphics compositor and garment pattern CAD are different capabilities.

Generator acceptance must show that the same versioned code, assets, parameters and seed reproduce the same approved design file under a recorded environment. Different seeds alone do not prove different visual output. Review collision/similarity detection, curation, print/placement validation, origin records and issuance/replacement policy before making public uniqueness claims.

## Mandatory evaluation floor and workflow-specific thresholds

The base requirements and hard failure floor are mandatory. Numeric workload/performance targets must be fixed for the declared workflow and comparator profile before confirmation; they are not measured results or brand approval requirements:

- Every mandatory core scenario has a fixture, observable assertions, expected failure behavior and retained evidence; all must pass before the core gate.
- Scripted isolation, permission, stale-approval and budget tests allow no unauthorized read, write or paid dispatch. Any observed violation blocks release.
- Every seeded must-fail review defect is detected, and a revision cannot inherit approval for changed content. Open-ended model quality uses a reviewed rubric and a recorded evaluation set.
- The owner completes intake, team/board changes, review/revision, model settings and stop/recovery flows through the UI without editing configuration files.
- Every evaluated run exposes its state, task owner, selected configuration, costs or unresolved reservations, output versions and recovery status. Unknown provider outcomes remain visible.
- Recovery tests preserve accepted artifacts and reconcile pending actions. Throughput, responsiveness, queue fairness and restore-time targets are set after a measured hardware/workload baseline, before the corresponding performance gate.
- Every seeded CORE-19 material dependency effect propagates; unchanged independent outputs are preserved and permission changes cannot be bypassed by historical acceptance.
- Every CORE-20 supported packet passes its manifest, intended-edit and source/preview/check identity assertions; unsupported checks and remaining limits stay visible.
- CORE-21–24 meet the preregistered parity-or-better floor on the strongest eligible configured baseline for the same supported goal, with declared quality, privacy/model and cost constraints. Setup, review and recovery assistance count. A 30% effort reduction is not a mandatory universal threshold.
- CORE-22/23 preserve permitted state and obligations through failures and takeover, disclose incurred costs/unknown liabilities, recheck current authority and permit bounded recovery. Any observed secret/derived-content leakage, unauthorized effect, false completion, blind duplicate, lost accepted state or broken cost ceiling blocks the gate regardless of other scores.
