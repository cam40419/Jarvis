# Platform baseline quality implementation plan

Implementation checkpoint: generic delivery packets now capture immutable multi-file
manifests, original bytes, escaped text previews, check/decision/review-state evidence and
declared limitations, with durable receipts and fresh export authorization. Human-only
artifact acceptance and source coverage now invalidate on full source-authority changes;
known revoked dependencies block disclosure and downstream execution. These are partial
BASE-01/02/04/05 foundations, not acceptance of CORE-19 through CORE-24. Field-level and
transitive impact/repair, required-file package acceptance, native editing/render checks,
resource accounting, continuity and comparative fixtures remain outstanding. Implemented
limits and behavior are recorded in the [artifact runbook](../runbooks/native-artifacts.md).

Confirmed owner direction, **October 10, 2026**. The five capabilities below are mandatory
base-platform requirements. They are not optional differentiation bets, future research
features or reasons to narrow Simon to one commercial workflow. The base platform must
match or exceed comparable platforms serving the same goal within its declared supported
scope. Comparative acceptance is part of core completion, not a substitute for it.

The [roadmap](../next-phases.md) owns delivery order and implementation status. This plan
extends the [platform backlog](autonomous-work-platform-plan.md#first-implementation-backlog),
[core acceptance matrix](clothing-brand-pilot-charter.md#core-acceptance-matrix) and
[connector/output contracts](integration-delivery-plan.md). The October 9 research supplies
dated competitor evidence; its five proposed opportunities are now baseline obligations.

## Scope and implementation boundary

Build the general project/company platform first: shared work, configurable agents/models,
artifacts, review, authority, resources, durable execution and usable administration. Use
representative research, software and creative project fixtures to validate reusable behavior.
A focused fixture is a measurement instrument, not a restriction of the product ambition.

The core includes dependency/change records, multi-file delivery manifests, preservation of
editable originals, preview/check interfaces, review decisions, recovery/reconciliation and
permission-aware handoff. Exercise these with supported generic files, bounded file operations
and deterministic providers. Include real model-quality evaluation within the enrolled
configuration and approved cap. Core tests must demonstrate actual supported artifacts and
user flows, not only the existence of a schema or a proposed screen.

Real Office/design/CAD authoring, publishing and commerce still enter one accepted tool at a
time after the core gate. The base must already represent, preserve, inspect and hand over
supported imported files and packages. Each new tool implements these contracts and proves
its actual output/edit/render behavior before enablement. A core fixture does not certify
all applications; a tool's unsupported format cannot be advertised as supported delivery.

### BASE-01 Change impact and repair

Implement versioned facts/requirements, typed dependencies from source fields/passages to
tasks and artifact components, impact records and bounded repair plans. Capture dependency
coverage and unresolved relationships explicitly. Model suggestions can help construct
the graph; they cannot suppress mandatory source/permission/policy invalidation.

A source, requirement or authority change must identify affected work, explain why it is
affected, preserve historical decisions and route the smallest justified correction. Freeze
or reopen pending releases that reference obsolete inputs. Preserve unaffected artifact
bytes and decisions; verify that repairs do not introduce collateral defects. If dependency
coverage is uncertain, mark that uncertainty and require conservative re-review.

Separate historical acceptance, current applicability, current disclosure permission and
external-release state. An old approval remains a historical record; it cannot certify
changed content or grant fresh publishing authority.

**Completion evidence:** change a price, material/unit and requirement independently; include
an irrelevant edit, conflicting source, revoked source and deliberately missing dependency.
Mandatory impacts are detected before acceptance/release, repaired outputs satisfy the new
requirements, unaffected fixtures remain intact and unknown coverage is visible. Retain
false-alarm and human-effort measurements rather than optimizing for fewer alerts alone.

### BASE-02 Usable delivery packets

Implement an immutable versioned package manifest linking the editable original/source,
supporting assets, rendered preview when supported, evidence, validator results, decisions,
producing task/run/configuration and unresolved limits. Individual files keep their own
identities and hashes; the package has its own revision and acceptance binding. Download,
export and re-open must reference the same intended revisions.

Preserve imported editable sources even when automated authoring is unavailable. Never
substitute a flattened preview for a promised editable source. The format profile states
application/renderer versions, required assets/fonts, supported editing operations and
validators. Label unavailable checks or rendering explicitly. Package admission accounts for
all source/preview/extract/revision bytes and applicable storage limits.

**Completion evidence:** assemble a supported multi-file fixture from real generic originals,
change a designated field/object, save/reopen it and verify source/preview/manifest identity.
Detect a missing source, stale preview, mismatched hash, omitted dependency and failed check.
An authorized receiver can inspect/download the useful package without reconstructing it.
Each later native application tool repeats the test in the promised application.

### BASE-03 Lower review effort

Implement a decision inbox with meaningful content/field/visual differences as supported,
material findings, evidence links, check coverage and explicit next decisions. Show missing,
omitted or truncated evidence. Group related reviews without losing each asset's identity
or decision rights. Carry concrete feedback into linked repair work and fresh review.

Measure briefing, inspection, correction and exception-handling effort. Stop or escalate
non-converging repairs instead of generating an unlimited review queue. Review admission
and notifications must account for the owner's capacity; fewer visible prompts cannot hide
unchecked work. Preserve independent review and current-authority gates.

**Completion evidence:** a user reviews and corrects matched fixture packets through the UI;
blind checks find seeded material defects, changed bytes require appropriate new acceptance,
and recurring owner review effort meets the comparative baseline. Quality/check coverage
cannot be weakened to improve review time. A 30% improvement remains an optional stretch
experiment from the research, not the definition of completing this requirement.

### BASE-04 Reliable completion

Implement or complete durable admission, checkpoints, correlation, operation receipts,
lease fencing, cancellation races, restore quarantine and reconciliation. Distinguish known
success/failure from an uncertain model/tool effect. Retry the same operation identity
without blindly duplicating a possibly completed effect. Revalidate payload, account,
destination and current authorization before dispatch.

Keep all incurred execution/review/repair charges and unresolved liabilities visible. Every
resource class admitted by the core requires its enforcing service, metering and accounting
to pass before CORE-ACCEPT, including applicable model, compute, storage and reference-tool
resources. Each later application tool must account for and enforce its additional resources
before individual acceptance. Distinguish
monetary liability, possibly live execution and queued work; prove that recovery remains
bounded and unrelated projects can progress. A timeout is not evidence that an old call
ended, and a zero token price does not remove resource usage.

**Completion evidence:** crashes before/after dispatch, lost responses, delayed results,
revoked authority, duplicate events, expired leases, concurrent caps, quota exhaustion and
restore all preserve correct identity/accounting. Test zero-fee unknown calls and reserved
future-review capacity for workspace starvation. Reconciliation or trusted termination
evidence restores permitted progress without clearing unsupported debt or redispatching
uncertain work. Measure recovery time and human intervention against the declared baseline.

### BASE-05 Continuity

Implement authorized takeover/export/import records containing current objective, sources,
facts, editable package revisions, decisions, responsible roles, pending work, checkpoints,
uncertain effects and costs. A new person or runtime can resume supported work from this
state. Keep agent role identity separate from its selected model/runtime; replacement
does not erase history or silently inherit broader authority.

Recheck permission for originals, extracts, derived claims, memory, previews and exported
packages. Historical retention does not imply current disclosure. Preserve permitted audit
metadata while applying the required content-revocation/retention rules. Transfer credential
references only where permitted; never export secrets or treat a prior decision as a
transferable grant. Re-enroll tools and reconcile pending effects at the receiving boundary.

**Completion evidence:** a second authorized human and a replacement supported runtime
resume a project without the maker's private explanation. Seed changed membership, revoked
evidence, an altered file and an unresolved effect. No inaccessible information leaks, no
effect is repeated blindly and missing context/unsupported transfer is visible. Measure
takeover effort and state completeness against the comparable workflow.

## BASE-06 Comparative acceptance

The goal is a base platform at least as good as the strongest relevant alternative for
each supported workflow and material capability. Do not reduce it to beating one weak
default setup, a generic benchmark score or a claim that another product lacks a feature
because its documentation is incomplete.

1. Maintain a capability/workflow comparison register using the [dated market map](../research/2026-10-09/README.md).
   Include relevant general project agents, existing workspaces and specialist proofing/
   production systems where they solve that workflow, plus a competent practitioner using
   an existing stack. Record why each comparator is eligible and any unavailable evidence.
2. Freeze supported inputs/outputs, model quality, privacy, permissions, budget, hardware,
   edition/configuration, operator setup and attempt/time limits before comparison. Permit
   competitors' native strengths and documented configuration. Separate controlled component
   checks from complete product-workflow trials.
3. Pre-register per-workflow quality, native usability, change correctness, human review/setup/
   takeover effort, completion/recovery, responsiveness and total-cost measures. Use the
   strongest eligible observed baseline per material measure; no aggregate score may hide
   a baseline defect. Define materiality margins and statistical handling before seeing
   confirmatory results; unmeasured claims remain open acceptance items.
4. Retain every attempt and hard failure. Acceptance requires the mandatory safety/data/
   accounting scenarios to pass and comparative evidence meeting the registered parity-or-
   better floor. Where evidence cannot rule out material regression, gather more evidence
   or improve the implementation before accepting that capability. Do not relabel a required
   base capability as optional to pass the gate.
5. Repeat held-out cases and test generality with non-apparel fixtures. Record tested versions,
   configuration, costs, raw outputs and blinded findings. Re-run affected comparisons after
   material model, validator, runtime or workflow changes. Add a newly relevant comparable
   platform to the register when it changes the baseline.

The [evaluation protocol](../research/2026-10-09/evaluation-plan.md) supplies screening,
repeatability and cost methods. Its full six-job creative matrix requires individually
accepted tools; the core comparison uses genuinely supported core workflows and imported
artifacts. The initial shortlist is a test-selection aid, not a permanent exemption from
the strongest relevant competition. Missing account access is a recorded evidence gap,
not a competitor failure or a completed comparison.

## Delivery order and status

1. Specify BASE-01/02/05 data/permission/manifest contracts, comparative scope and fixture
   rubrics alongside remaining tenant/admin/resource work. Preserve the useful existing
   execution/review contracts and tests.
2. Complete BASE-01/02/03 in the shared project/artifact/review services and UI; complete
   BASE-04/05 recovery, accounting, revocation and takeover. Exercise cross-package behavior
   with the reference provider and supported files.
3. Run the mandatory CORE-01 through CORE-24 program and BASE-06 comparative checks. Resolve
   failures and remaining material evidence gaps; owner acceptance follows demonstrated
   behavior, not a roadmap label. Then reach CORE-ACCEPT.
4. Implement and accept one real tool at a time. Each tool inherits BASE-01 through BASE-05,
   performs format/provider-specific checks and refreshes the relevant comparative evidence.
   Hosted/commercial release remains its own operating gate.

Current immutable revisions, bounded text review/repair, task/source authority fencing,
model liability records and PostgreSQL checkpoints support this work. They do not complete
selective cross-output impact, multi-file native delivery, a measured review experience,
complete recovery economics or permission-safe cross-runtime continuity. Keep those gaps
explicit until their acceptance evidence exists.

Later innovation work must add value beyond this baseline. Project branches, bounded
business simulation, verified procedure compilation and consented learning remain research
avenues with separate decisions; they do not excuse incomplete base behavior.
